## 1. 为什么有三种数据（先搞清这个，后面就不绕了）

因为模型"认识"哪种机器，取决于它用什么数据练过。而世界上有三种"挖掘机身体"：

| | ① 合成数据 | ② 真机数据 | ③ AGX 仿真数据 |
|---|---|---|---|
| **什么机器** | 纸上画的假想机（几个数学公式，没土、没液压） | 真挖掘机（山河 SWE600F，有液压、有土） | 电脑里的仿真机（AGX 物理引擎，有颗粒土） |
| **怎么来的** | 程序自己编题自己解，10 分钟出上万条 | 真机上的传感器录的（液压阀电流等） | 在 AGX 仿真里自动挖，录下来的 |
| **谁产的** | **他们自己**（算的，不用机器） | **他们自己**（要在真机上采） | **只能我们产**（AGX 装在我们机器上） |
| **解决什么** | 学"挖掘的大致套路" | 学"真机器的力道"（他们的部署目标） | 学"仿真机的物理"（我们验收他们的考场） |

**接力关系**：①练套路（便宜）→ ②在真机上纠偏（他们的活）→ ③在仿真机上适应
（我们的活，因为只有我们有这台仿真机）。他们之前给我们的模型只练过①和②，
没在 AGX 这台"机器"上练过——所以拿到我们这里跑不好。**给它③的数据，它才能
在我们这里干活。**

> 这三种不是重复劳动。打个比方：①看教材背套路、②真车实操、③在 VR 模拟器里
> 练——因为最终考试在 VR 模拟器里，所以 VR 的练习素材必须我们录。
> 教材和真车训练学校自己安排。

**补一句**：③我们已经采好了（103 条有效循环，在 `data/raw/run_all/`），
**不需要再采**。详见 §4。

## 2. 一条数据长什么样（真实文件对照）

下面全部用同一条真实循环（ep_0000）的数字。

### 2.1 我们采的：一条 = 一个 npz 文件（一条循环 = 120 拍）

文件：`data/raw/run_all/ep_0000_teacher.npz`

| 字段 | 形状 | 真实样例 |
|---|---|---|
| `joints_before` | (120, 4) | 拍 0：`[-0.0000, -0.0097, 0.0000, -0.0004]`；拍 47：`[1.886, -0.085, -0.23, -0.674]` |
| `joints_after` | (120, 4) | 拍 0：`[0.0845, -0.0015, 0.0000, -0.0000]`；拍 47：`[1.886, -0.105, -0.166, -0.678]` |
| `scoop` | (120,) 真假 | 拍 0 = 假；**拍 47 = 真（这一拍装上了土）** |
| `beat_seconds` | (120,) 秒 | 这一拍实际花了多久 |
| `meta`（一小段 JSON） | — | 挖点 `(-1.74, 5.34)`、卸点 `(1.90, 5.46)`、关节名、单位声明 |

**三个关键点**：
1. 单位是**机器原生**的：`swing` 是弧度；`boom/arm/bucket` 是**液压缸伸出去多少米**；
2. 4 列的顺序固定是 `swing, boom, arm, bucket`；
3. "拍"不是固定时间——是"动作走到位"一次。120 拍 = 一个完整循环
   （对准→下挖→收斗→摆转→卸料）。

### 2.2 他们训练用的：同一条循环 = 一个 h5 文件（120 帧，帧=拍）

文件：`episode_000000.h5`（由上面那条 npz 转出来的；转换见 §3）

| 字段 | 形状 | 真实样例 |
|---|---|---|
| `observations/state` | (120, 35) | 帧 0 的第 6~9 列 = `[-0.0, -91.1, -207.5, -248.7]`；帧 47 = `[108.1, -99.4, -247.7, -421.9]`——**度**（其余 31 列全 0） |
| `actions/joint_increment` | (120, 16, 4) | 帧 0 的第 0 行 = `[4.842, 0.904, -0.002, 0.09]`：**第 0 拍这一拍里，四个关节各动了多少（度）**；再往下 15 行是未来 15 拍的 |
| `annotations/phase` | (120,) | 帧 0 = **2**（还没装土）；帧 47 = **4**（装上了，该去卸了） |
| `annotations/goal` | (120, 6) | `[-1.74, 5.34, 0.0, 1.90, 5.46, 0.0]` = 挖点 xyz + 卸点 xyz（米） |
| `annotations/valid` | (120,) 真假 | 有效帧（我们全填"真"） |

### 2.3 对应关系记住三句话就够

1. **我们的 `joints_before[47]` = 他们的 `state[47]`**（只是米/弧度换成了度）；
2. **我们的 `after[47] − before[47]` = 他们的 `increment[47, 第 0 行]`**（一拍的动作量）；
3. **我们的 `scoop[47] = 真` → 他们的 `phase[47] = 4`**。

其余字段（补零掩码、有效性、文件属性）都是工程细节，附录 §8.1 有全表。

## 3. 转换怎么转的（7 步，用拍 47 走一遍）

用拍 47 的真实数字（`before = [1.886, -0.085, -0.23, -0.674]`）：

| 步骤 | 做什么 | 拍 47 的结果 |
|---|---|---|
| 1 | **对齐时间轴**：不重采样。我们的"拍"就是他们的"帧"，1 拍 = 1 帧 | 拍 47 → 帧 47 |
| 2 | **单位换算**（用"标定文件"这一把尺，全局唯一换算点） | swing：`1.886 弧度 ×57.3 = 108.1 度`；boom：`-0.085 米 → -99.4 度`（**注**：现在这把尺是占位值，标定后数字会变，机制不变） |
| 3 | **写状态**：35 列的矩阵全填 0，只把 4 个角度放进第 6~9 列 | `state[47] = [0,0,...,0, 108.1, -99.4, -247.7, -421.9, 0,...]` |
| 4 | **生成增量**：把每拍的位形变化算出来，从每一帧起存"未来 16 拍"的 | 拍 0：`after−before = [0.0845, 0.0082, ...] → [4.842, 0.904, ...] 度` |
| 5 | **写相位**：看载料真值，没装土写 2、装上了写 4 | 拍 47 装上了 → `phase[47] = 4` |
| 6 | **写目标**：挖点/卸点补上地面高度（z）变成 6 个数，铺满 120 帧 | `[-1.74, 5.34, 0, 1.90, 5.46, 0]` |
| 7 | **收尾**：写文件属性（单位、时间轴、标定状态…），顺带导出一份**他们训练配置要用的建议值** `suggested_config.json` | — |

> 为什么单位换算要先"标定"：我们的机器说"缸伸出 0.085 米"，他们的模型说
> "臂转了 -99 度"——米变度靠一把尺量出来（在 AGX 里扫一遍缸、量齿尖）。
> 现在用的是估的尺，所以产出的文件标记"未标定、禁止训练"。
> **尺一量好，原数据重新转一遍（几分钟，一条命令），数字就都是真值了。**

## 4. 现在哪里对上了、哪里还不对、还缺什么

### 4.1 已经对上的（不用再动）

- 文件与字段（`episode_*.h5`、`observations/state`、`actions/joint_increment`、
  `annotations/valid`）：形状、命名、类型全对——**他们载入器实测 103/103 直读通过**；
- 时间轴（拍=帧）、单位（状态用度、增量写度，他们的自动识别实测正确）；
- 相位和目标的设计（2/4 规则、6 维目标）。

### 4.2 还不对的三处（都有明确的修复办法）

**① 量尺还是占位值（值不对）**
- 现状：换算文件 `calibrated: false`——现在 h5 里所有的"度"都是估的；
- 后果：他们训练里的"末端轨迹一致性"损失和自评都用自己的几何公式算——
  尺不对，这些信号算出来就是错的；训出的模型将来在 AGX 上的动作换算会系统性偏；
- 修复：**等 AGX 许可证 → 我们扫缸标定（半天）→ 重新转换（几分钟）**。
  原始 103 条采集原样复用，不用重采。

**② 他们的载入器暂时不读我们写的"目标和相位"（行为没对齐）**
- 现状：`annotations/goal`、`annotations/phase` 这两列会被**静默忽略**——
  他们训练会用公式反推的近似目标 + 时间平分的相位（和我们部署时给的 2/4 不一样）；
- 后果：训练时见到的条件和部署时给的条件不是一回事，性能打折；
- 修复：他们加约 **6 行代码**优先读这两列（样例在本文档 §8.4，可直接粘贴）。

**③ 他们的 AGX365 训练配置还没建（参数没填）**
- 需要填四个值：三段臂长（=我们的标定结果）、关节活动范围（=我们数据实际范围）、
  每步动作上限（=我们导出的建议值）、机器名（两处写成同一个字符串）；
- 不填的后果：前两个不对，他们的程序**直接拒绝加载数据**；动作上限沿用旧值，
  部署跑起来会慢好几倍；
- 修复：拿我们标定后的数字建一份配置（他们的活，半小时）。

### 4.3 还缺什么（一条线）

```
AGX 许可证（外部）
  → ① 标定（我们，半天）
  → ② 重新转换 + 导出建议配置（我们，几分钟）
  → ③ 他们建配置 + 加 6 行代码 + 用我们的数据重训（他们的关键路径）
  → ④ 我们接入 + 10 个留出点验收（脚本现成，≥7 通过）
```

**明确不缺的**：数据（103 条早就采好）、格式（不用再改）、
转换器/接入适配器/验收脚本（都已经建好并实测过）。

**最大的不确定性不在格式**：他们现有的模型连自己团队的测试都没过
（官方评估里"挖到点/卸到点"都是 False，挖点偏差约 1.4 米、合格线 0.15 米）。
格式和补丁解决"接得对"，模型质量解决"答得对"——后者要靠他们重训。

## 5. 名字对照表（读不懂的根源）

| 说人话 | 大脑组叫法 | 小脑组叫法 |
|---|---|---|
| 走一步动作 | **拍**（一条循环 120 拍） | **步 / 控制周期**（约 118 步） |
| 挖的位置 | **挖点**（`dig_x_m`, `dig_y_m`） | **pick 点** |
| 倒土的位置 | **卸点**（`dump_x_m`, `dump_y_m`） | **place 点**（不叫 dump） |
| 铲斗装没装土 | **`scoop`**（载料真值，>50kg） | *没这个概念* |
| 动作进行到哪段 | *没这个概念* | **`phase`**（0~7 阶段） |
| 四个关节 | 同名，但值是**原生单位**：swing=弧度，三缸=**米** | 同名，但值是**转角（度）** |
| 模型输出 | 绝对目标（下一拍站到哪） | 增量（比现在再多转多少） |
| 数据文件 | `*.npz`（原始） | `episode_*.h5`（训练用） |
| 模型文件 | `pretrained_model/` 目录 | `*.pt` |

> ⚠️ **最危险的词：`boom`（`arm`、`bucket` 同理）。**
> 我们说 "boom = -0.085"，指的是**液压缸伸出 -0.085 米**；
> 他们看到同一个数，默认意思是**臂转了 -0.085 度**。完全不是一回事。
> **这一切由"标定文件"负责翻译**——它是训练和部署共用的同一把尺。

## 8. 附录：工程细节（给要动手的人）

### 8.1 h5 字段全表（我们转换器的产出 = 他们载入器实际读的）

| 数据集路径 | 形状/单位 | 含义 | 他们读吗 |
|---|---|---|---|
| `observations/state` | (T,35)；第 6~9 列**度**，其余 0 | 每帧的四关节状态 | ✅ **必需** |
| `actions/joint_increment` | (T,16,4)；**度** | 未来 16 帧的每帧增量 | ✅ 可选但保留（缺了他们自己用差分重算） |
| `annotations/valid` | (T,) 真假 | 有效帧 | ✅ 可选（缺省全真） |
| `annotations/goal` | (T,6)；米 | 精确的 pick/place xyz | ❌ 现在被忽略（§4.2②） |
| `annotations/phase` | (T,)；2/4 | 相位标签 | ❌ 现在被忽略（§4.2②） |
| `annotations/action_pad`、`joint_rad`、`goal`、`phase` | — | 补零掩码/调试用副本 | ❌（保留无害） |

文件属性：`timeline=beats`、`control_frequency=10`（名义）、`chunk_size=16`、
`history_length=10`、`calibrated`、`unit_joint_increment=deg`、`phase_mode` 等。
文件命名 `episode_000000.h5` 起；他们只扫一层这个通配符（不递归）。

**单位为什么这么定**：状态用度是他们的设计；增量写"度"是因为他们的载入器用
"99% 的数超过 0.5 就当度"这个规则自动识别单位——度制在正常和大动作两种幅度下
都能被正确识别（弧度制遇到大摆转会被误判）。

### 8.2 标定文件（那把"尺"，训练和部署共用）

模板：`configs/machine_agx365.template.json`；工作副本 `data/machine_agx365.json`。
内容：四个关节的原生单位声明、swing 零位偏移、每缸"位移（米）↔ 角度（度）"映射、
挖/卸点的地面高度。`calibrated` 字段只有变成真，转换器才接受（防污染训练数据）。
标定方法：`scripts/agx_machine_fit.py`（文档头写了采样格式；拟合器带自测，
残差超 0.05 米会拒绝出文件）——许可证恢复后半天完成。

### 8.3 五条一致性红线

1. **换算只有一个来源**：米↔角度只走标定文件，训练和部署用同一份；
2. **拍 = 步 = 帧**：不重采样、不二次切分；
3. **相位同源**：训练标签和部署估计都是 2/4 规则；
4. **目标语义**：挖点/卸点 = pick/place，同一对坐标；
5. **关节顺序**：`swing, boom, arm, bucket` 三处一致（对不上我们的适配器
   **直接报错**，不会默默出错）。

### 8.5 FAQ

- **为什么不能直接吃我们的 npz？** 单位（米/弧度 vs 全角度）、动作（绝对 vs 增量）、
  条件（4 坐标 vs 6 坐标+相位）都不同——转换器就是干这个的（已经做好了）。
- **为什么步长上限不能沿用旧值？** 他们的旧值是合成数据的步长（约 2.5°）；
  我们的"拍"是大步（可达 20°+/拍）。推理端按旧值截断 = 每拍只让走一小步，
  一个循环慢好几倍。用我们 `suggested_config.json` 里的值。
- **为什么必须先标定？** 不标定，"米↔度"就是拍脑袋——训练数据语义错位，
  训出来的模型对不上部署换算。
